## 3. Блок A — исправления

### A1. Сохранённый договор показывает не ту цену (критично)

**Проблема.** `resolveOrderDisplayCalculation` в `apps/web/src/lib/orders.ts`: для сохранённой версии режима `check_contract` цена берётся из текущего `order.contract_price`, а себестоимость и маржа из снимка. Если после сохранения изменить цену договора, цифры расходятся, и принцип «зафиксированные версии неизменяемы» нарушается. В ветке «живого» расчёта аналогичная подмена лишняя: `calculate` уже использует `contractPrice`.

**Решение.**
1. Для `source: "saved"` всегда `priceTotal = normalized.priceTotal`, `margin` и `marginPct` из снимка. Убрать подмену.
2. Убрать лишнюю подмену в ветке `source: "live"`.
3. Добавить в `OrderDisplayCalculation` поле `contractPriceMismatch: { snapshot: number; current: number } | null` (не `null`, только если версия в режиме `check_contract` и `order.contract_price` отличается от цены снимка).
4. В интерфейсе при `contractPriceMismatch` показать заметную плашку: «Цена договора в заказе (X ₸) отличается от версии №N (Y ₸). Сохраните новую версию или пересчитайте по актуальным данным».

**Тесты (сначала падающие)** в `orders.test.ts`:
- версия `check_contract` с ценой 850 000, `order.contract_price` = 900 000 → отображается 850 000, маржа из снимка, `contractPriceMismatch` заполнен;
- цены совпадают → `contractPriceMismatch === null`;
- режим `quote` не затронут;
- живой расчёт возвращает цену из `calculate` без подмены.

**Приёмка.** Сохранённая версия не меняет цифры при правке цены договора; плашка видна; кнопка «Пересчитать по актуальным параметрам» показывает новые цифры.
**Как проверить владельцу:** открыть заказ с сохранённой версией договора, изменить цену договора в шапке, убедиться, что цифры версии остались прежними и появилась плашка.

### A2. «Минимальная цена» может быть ниже целевой маржи (критично)

**Проблема.** `minimumPrice` в `packages/calc/src/index.ts` округляет цену «половина вверх» (`roundHalfUp`). Цена может оказаться на несколько сотен тенге ниже расчётного минимума. В прогоне на ~14 тыс. случайных заказов около половины дали маржу ниже 18%, худший случай 17,8%. Предупреждение `check_contract` использует тот же порог, поэтому договор на «минимальной» цене может иметь маржу ниже цели без предупреждения.

**ПОДТВЕРДИТЬ у владельца.**
- **Вариант A (рекомендация ревью):** округлять цену **вверх** до шага `priceRounding`. Маржа гарантированно не ниже цели. Эталон меняется: расчётная цена 861 000 → **862 000** (точный минимум ≈ 861 008), себестоимость ≈ 706 210, маржа ≈ 155 790 ₸ (≈ 18,07%). В режиме `check_contract` (850 000 ₸) цифры те же, меняется текст предупреждения на «договор ниже минимальной цены 862 000».
- **Вариант B:** оставить округление как есть, переименовать в «расчётную цену» и всегда показывать предупреждение, если фактическая маржа ниже целевой: «маржа ниже целевой на X п.п.».

**Решение (для варианта A).**
1. Добавить `roundUpToIncrement(value, increment)` с той же защитой от погрешности float, что в `roundKztUp`.
2. `minimumPrice` использует её вместо `roundHalfUp`. `roundHalfUp` остаётся, если нужен где-то ещё; иначе удалить вместе с тестами.
3. Обновить эталон в `README.md`, `SPEC.md` и тестах.

**Тесты.**
- эталон из README с новыми цифрами;
- инвариант на 10 000 случайных наборов (фиксированный seed): `priceTotal >= fixedCost / denominator` и `priceTotal - fixedCost / denominator < priceRounding`;
- явный тест на границу: когда `fixedCost / denominator` равно кратному шагу, цена не увеличивается лишний раз.

**Известное допущение (ПОДТВЕРДИТЬ):** сборка, технолог и резерв округляются вверх по отдельности (`roundKztUp`), что может уменьшить маржу не более чем на 3 ₸. Считаем допустимым.

### A3. Защита от абсурдных результатов (критично)

**Проблема (воспроизведено).**
- Скидка больше стоимости заказа даёт отрицательную цену (−9 843 000 ₸) без предупреждения, при этом `marginPct` положительный (0,83).
- Резерв на риск 60% при сумме долей < 100% даёт цену 14,3 млн на себестоимость 500 тыс. `save_parameters` проверяет только сумму долей `< 100%`.
- Корректировки себестоимости могут сделать затраты отрицательными.
- Индивидуальные настройки заказа (`orders.settings`) вообще не проходят проверку суммы долей.
- В нижней панели любая ошибка расчёта, кроме одной, показывается как «Необходимо указать цену по договору» (в том числе `invalid_input`).

**ПОДТВЕРДИТЬ у владельца.** Максимальная сумма долей (маржа + сборка % + технолог % + резерв). Рекомендация: **0,80** (цена не больше, чем в 5 раз выше постоянных затрат). Значение хранится как одна константа `MAX_PRICE_SHARES_SUM` в `packages/calc` и дублируется в SQL с комментарием «держать в синхроне».

**Решение.**
1. `packages/calc`: новые ошибки в `CalculationOutcome`: `price_not_positive` (режим `quote`, итоговая цена ≤ 0) и `parameters_share_too_high` (сумма долей выше `MAX_PRICE_SHARES_SUM`).
2. Предупреждения (не блокируют): отрицательные постоянные затраты («корректировки сделали затраты отрицательными»), цена договора равна 0.
3. Миграция `013`: заменить `save_parameters` с той же проверкой по `MAX_PRICE_SHARES_SUM`.
4. UI: валидация сумм долей при сохранении индивидуальных настроек заказа теми же функциями.
5. UI: нижняя панель показывает отдельный понятный текст для **каждого** кода ошибки. Сделать проверку на исчерпанность (`never`), чтобы новый код без текста не компилировался.
6. `shouldConfirmCalculationSave`: требовать подтверждение также при отрицательной марже.

**Тесты.** По одному на каждый пункт выше, включая граничное значение суммы долей (ровно максимум проходит, чуть больше не проходит); SQL-тест `save_parameters` на ту же границу.

### A4. Блокировка заказа только в интерфейсе (важно)

**Проблема.** `isOrderLocked` проверяется только в React. База позволяет менять и удалять `order_items`, `order_lines`, `adjustments` у заказа в статусе `approved` и выше. RPC `apply_price_updates_to_order` статус не проверяет. Пока владелец один, риск небольшой; при появлении сотрудников или агентов станет критичным.

**ПОДТВЕРДИТЬ у владельца.**
- Статусы блокировки: как в интерфейсе (`approved`, `in_production`, `done`, `cancelled`)?
- Можно ли менять `contract_price` и `settings` у заказа после `approved`? Рекомендация: нет, только через «Открыть для правок» (перевод в `quoted`).
- Можно ли удалять заказ в статусах `approved` и выше? Рекомендация: нет.

**Решение.** Миграция `014`:
1. Функция-триггер на `order_items`, `order_lines`, `adjustments` (INSERT, UPDATE, DELETE): определить `order_id` (и старый, и новый при UPDATE), прочитать статус заказа, при заблокированном статусе выбросить исключение с понятным текстом. **Если заказ не найден (каскадное удаление) — разрешить.**
2. Триггер на `orders` (UPDATE): при заблокированном статусе запретить менять `contract_price`, `settings`, `name`, `client_label`; смену `status` (в том числе разблокировку `approved → quoted`) разрешить.
3. Таблицы `actual_expenses`, `payments`, `calculations` (включая `set_contract_baseline`) остаются доступными во всех статусах: факт вносится после утверждения.
4. `formatErrorMessage`: понятное сообщение «Заказ утверждён и заблокирован для правок».

**SQL-тесты** (`supabase/tests/order_lock.sql`): в `approved` вставка, изменение и удаление позиции запрещены; в `quoted` разрешены; разблокировка `approved → quoted` работает; платёж и расход в `approved` разрешены; удаление `draft`-заказа каскадом проходит; `apply_price_updates_to_order` на заблокированном заказе падает.

### A5. Сохранение падает при сильно отрицательной марже (важно)

**Проблема.** `calculations.margin_pct` имеет тип `numeric(6,4)`, максимум 99,9999. При цене договора, на два порядка меньшей себестоимости (опечатка «850» вместо «850 000»), маржа ≈ −827, и вставка падает с ошибкой переполнения.

**Решение.** Миграция `015`: `alter column margin_pct type numeric(12,4)`. Представления на эту колонку не ссылаются. В интерфейсе значения ниже −999% показывать как «< −999%».

**Тесты.** SQL: вставка версии с `margin_pct = -999.185` проходит. TS: форматирование крайних значений.

### A6. План/Факт и экспорт по-разному считают переделки (важно)

**Проблема.**
- `sumExpensesByCategory` исключает переделки, поэтому в таблице «План/Факт» категории не включают переделки, а итог (`totalExpenses`) их включает: сумма строк ≠ итог.
- SQL-представление `v_accounting_export` включает переделки в категории. Цифры в приложении и в экспорте расходятся.
- Строки «Резерв на риск» и «Корректировки» всегда имеют факт 0, поэтому в «разнице» вечная «экономия».
- `FactTab.tsx:73`: `res as any`. Функции `computeActualMargin` и `sumAllExpenses` нигде не используются.

**ПОДТВЕРДИТЬ у владельца.**
- Считать ли переделки частью категории, к которой они относятся? Рекомендация ревью: **да** (сумма строк = итог = экспорт), а строка «из них переделки» остаётся информационной.
- Для строк «Резерв» и «Корректировки»: показывать только план, факт и разницу как «—». Сравнивать ли итог факта с планом целиком или без резерва? Рекомендация: с планом целиком (как сейчас), но с пометкой «в плане учтён резерв X ₸».

**Решение.**
1. `sumExpensesByCategory` не исключает `is_rework`.
2. `PlanFactRow.fact: number | null` (`null` для резерва и корректировок), в интерфейсе «—», разница не считается.
3. Заменить `as any` на типизированную функцию приведения `unknown → CalculationResultLike`.
4. Удалить неиспользуемые функции и их тесты.

**Тесты.** Сумма строк факта равна `totalExpenses`; строки резерва и корректировок имеют `fact === null`. SQL: в `accounting_export_view.sql` сумма всех категорий расходов равна `actual_expenses_total`.

### A7. Тихие «магические» значения при чтении снимков (важно)

**Проблема.** `normalizeCalculationParams`, `normalizeCalculationInput`, `normalizeCalculationResult` в `lib/orders.ts` при отсутствии поля подставляют значения вроде `0.18`, `0.145`, `35000`, `1000`. Повреждённая или неполная версия молча показывает выдуманные цифры. Это противоречит правилу `AGENTS.md` «числа не придумывать».

**Решение (после ответа на O4).**
1. Обязательные поля читаются из camelCase или snake_case (если O4 > 0); если нет ни там, ни там, выбросить `SnapshotCorruptedError` с именем поля.
2. UI: карточка версии показывает «Версия N: данные повреждены (поле X)», страница не падает, версия не используется как опорная для План/Факт.
3. Если O4 = 0, удалить поддержку snake_case и связанные тесты.
4. Дублирующиеся типы `Normalized*` заменить типами из `@kuhni/calc`, где это возможно без изменения поведения.

**Тесты.** Каждое обязательное поле: отсутствие приводит к `SnapshotCorruptedError`; «хороший» снимок читается без изменений; `resolveOrderDisplayCalculation` не падает на повреждённой версии.

### A8. Гигиена базы данных (после A1–A7)

**ПОДТВЕРДИТЬ у владельца** п. (б): можно ли запретить удаление версий расчёта и правку истории цен? Рекомендация: да.

Миграция:
1. **Права на функции.** `revoke execute on function … from public, anon` для всех функций схемы `public`; `grant execute … to authenticated` только для `is_owner`, `save_parameters`, `set_contract_baseline`, `apply_price_updates_to_order`.
2. **Неизменяемость истории.** `calculations`: запретить DELETE, кроме каскадного удаления заказа (тот же приём, что в A4: если заказ не найден — разрешить). `price_history`: запретить UPDATE и DELETE (только добавление).

4. `apply_price_updates_to_order`: принимать только одну форму ключей (`line_id`, `unit_price`), убрать алиасы `lineId`, `newUnitPrice`, `new_price`; обновить вызов в приложении.

**SQL-тесты:** анонимный и авторизованный не-владелец не могут вызвать RPC; удаление версии расчёта запрещено; каскадное удаление заказа проходит; правка `price_history` запрещена.
