## 2. Утверждённые правила бизнес-логики

1. **Расчёт прибыли проекта (Q4):**
   * $\text{Фактическая прибыль} = \text{Цена договора} - \text{Все фактические расходы (включая переделки)}$.
   * $\text{Рентабельность \%} = \text{Фактическая прибыль} / \text{Цена договора}$.
   * Кассовые показатели отображаются строго отдельно: $\text{Оплачено клиентом}$, $\text{Остаток долга} = \text{Договор} - \text{Оплачено}$, $\text{Кассовый баланс} = \text{Оплачено} - \text{Все расходы}$.
   * Переделки входят в общие расходы проекта, но под таблицей выводятся отдельной информационной строкой: *«из них переделки: X ₸»*.
2. **Отображение старых и сохранённых заказов (Q2):**
   * Если у заказа есть сохранённые расчёты, на экране отображаются данные **сохранённой версии**, а не живой пересчёт по текущим глобальным параметрам.
   * Живой пересчёт по актуальным параметрам доступен только по явному нажатию кнопки *«Пересчитать по актуальным параметрам»*.
3. **План в План/Факте (Q3):**
   * План строится по версии с отметкой `is_contract_baseline = true`. Если договорная версия не отмечена — по последней сохранённой версии.
   * В заголовке блока всегда выводится явная подпись: *«План: версия №X»*.
4. **Категории расходов (Q5):**
   * В таблицу `actual_expenses` добавляются две новые категории: `assembly` («Сборка») и `technolog` («Технолог»).
   * В таблице «План/Факт» выводятся все статьи сметы: Материалы, Цех, Фасады, Фурнитура, Транспорт, Работа, Сборка, Технолог, Резерв, Корректировки, Остальное. Сумма строк плана строго равна $\text{cost\_total}$.
5. **Режим «Проверить договор» (Q7):**
   * В этом режиме итоговая цена заказа строго равна сумме из поля договора. Блок ценовых скидок скрывается, так как скидки применяются только при формировании сметы в режиме «Рассчитать цену».
6. **Параметры и формулы (Q1):**
   * Сохранение параметров блокируется только в математически невозможном случае: сумма процентных ставок $\ge 100\%$ (знаменатель $\le 0$).
   * При марже $> 50\%$ или сумме ставок $> 70\%$ выводится визуальное предупреждение, но сохранение разрешено.
7. **Свобода управления заказом (Q9):**
   * Статус заказа и цену договора владелец может менять в любой момент без блокировок.
8. **Деплой (Q8):**
   * Деплой проекта осуществляется только через Vercel.

## 4. Критерии финальной приёмки всего ТЗ

1. **Тесты и сборка:** `npm test` проходит без единой ошибки во всех пакетах (`@kuhni/calc` и `@kuhni/web`). `npm run build` собирается без предупреждений.
2. **Эталонный расчёт кухни:** Кухня 3м на эталонных позициях из спецификации даёт расчётную цену **861 000 ₸**, себестоимость **706 025 ₸**, маржу **18,00%**.
3. **План/Факт:** Сумма всех отображаемых строк плана строго равна **706 025 ₸**.
4. **Управленческая прибыль:** При договоре 800 000 ₸, расходах 500 000 ₸ и предоплате 400 000 ₸ отображается:
   * Фактическая прибыль: **+300 000 ₸** (рентабельность 37.5%).
   * Оплачено: **400 000 ₸**, остаток долга: **400 000 ₸**.
   * Кассовый баланс: **−100 000 ₸**.
5. **Иммунитет старых заказов:** Смена глобальной маржи на странице «Параметры» не меняет цифры отображаемого сохранённого заказа.
6. **Безопасность Service Worker:** В Cache Storage браузера отсутствуют данные из базы данных Supabase. При логауте кэш очищается.
