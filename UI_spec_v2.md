# ТЗ: улучшение удобства интерфейса (UI v2)

Документ для агента-разработчика. Продолжение `UI_spec.md`. Основан на ревью интерфейса от 10.10.2026. Владелец код не пишет, проверяет результат на телефоне (375 px) и на ПК (1280 px) и принимает решения.

Ревью выполнено по коду, без запуска на устройстве. Пункты, помеченные **«проверить»**, нужно сначала подтвердить на реальном экране.

---

## 0. Правила для агента

1. Следовать `AGENTS.md` и правилам из `UI_spec.md` раздела 0 (маленькие шаги, коммит после шага, отчёт «что сделано / как проверить / что решить»).
2. **Расчёт не переписывать.** Интерфейс вызывает `@kuhni/calc`. Бизнес-логику не придумывать. Пункты **«ПОДТВЕРДИТЬ»** — вопрос владельцу до кода.
3. Начинать UX-шаги U1 и далее **после** шагов A1–A4 из `FIX_SPEC_2.md` (цена в сохранённых версиях, ошибки расчёта, блокировка заказов на уровне БД).
4. Каждый шаг заканчивается проверкой по чек-листу раздела 5 на ширине 375 px и 1280 px.
5. Поведение данных не менять: структура БД, RLS и неизменяемые версии остаются как есть. Если шагу нужна новая миграция, это явно указано.

## 1. Цель и измеримые критерии

**Цель:** владелец собирает эталонную кухню на телефоне в 2–3 раза быстрее и всегда понимает, что именно он сохраняет и какая цифра перед ним.

| Метрика | Сейчас (по числу действий) | Цель |
|---------|----------------------------|------|
| M1. Ввод эталонной кухни (25 позиций из прайса) на телефоне | около 4 действий на позицию, окно закрывается после каждой | не более 3 минут, не более 2 действий на дополнительную позицию |
| M2. Минимальный размер текста | 10–11 px в 28 местах, 12 px в 78 | не меньше 12 px для подписей, не меньше 14 px для основного содержимого и чисел |
| M3. Зоны нажатия | иконки ✎ 🗑 около 28 px | не меньше 44 × 44 px |
| M4. Перекрытие | панель итогов может закрывать нижнюю навигацию (**проверить**) | никогда не перекрывает навигацию и содержимое |
| M5. Начальная загрузка | один бандл около 640 КБ | начальный JS не более 350 КБ (до сжатия) |

**ПОДТВЕРДИТЬ у владельца:** состав эталонной кухни (список 25 позиций с количествами) для замера M1. Агент сохраняет его в `docs/benchmark-order.md`.

## 2. Принципы

1. Самое частое действие (добавить позицию) должно быть самым быстрым.
2. Один главный экран = одна задача. Второстепенное прячется, но не удаляется.
3. Всегда видно главное: цена и маржа. Детали по запросу.
4. Слова владельца, а не разработчика (раздел U6).
5. Ошибки не пугают и не блокируют лишнего; опасное действие можно отменить.

## 3. Шаги

Порядок: U0 → U1 → U2 → U3 → U4 → U5 → U6 → U7 → U8 → U9. Шаги U6 и U7 можно делать частями внутри других шагов.

### U0. Подготовка: разбить `OrderDetailPage.tsx` без изменения поведения

**Проблема.** Файл на 3193 строки: 80 `useState`, 24 прямых вызова Supabase, 7 модальных окон. Любое UX-изменение в нём рискует сломать соседнее.

**Решение.** Чистый рефакторинг, интерфейс снаружи не меняется:
- хуки данных в `apps/web/src/hooks/`: `useOrderData` (загрузка и состояние), `useOrderLines`, `useOrderCalculations` (живой расчёт, версии, фиксация);
- компоненты в `apps/web/src/components/order/`: `OrderHeader`, `ItemsSection`, `LinesSection`, `PricePicker`, `SummaryBar`, `HistoryTab`, `FactTab` (уже есть), модальные окна по одному файлу;
- обращения к Supabase только в хуках и `lib/`, не в разметке.

**Правила.** Один компонент за коммит; после каждого коммита `npm test` и `npm run build` зелёные и ручная проверка основных сценариев (создать заказ, добавить позицию, сохранить версию, внести расход). Файлы больше ~400 строк не допускаются.

**Приёмка.** Внешнее поведение идентично; `OrderDetailPage.tsx` не больше ~300 строк.

### U1. Быстрый ввод позиций (главный эффект)

**Проблема.** Путь «Из справочника» → поиск → тап по позиции → форма количества → «Добавить» → окно закрывается. Для 25 позиций около 100 действий, и справочник нужно открывать заново.

**Решение.**
1. Окно справочника (`PricePicker`) **остаётся открытым** после добавления. Вверху постоянно виден выбранный «текущий предмет заказа» (изделие, куда добавляются позиции), сменить можно одним тапом.
2. Каждая строка справочника содержит степпер количества прямо в строке:
   ```
   Петли EH7                      − 20 +
   шт · Фурнитура                 350 ₸
   ```
   Тап по «+» добавляет позицию (или увеличивает количество), «−» уменьшает; тап по числу открывает ввод с цифровой клавиатурой (`inputmode="decimal"`, запятая и точка допустимы). Шаг степпера по умолчанию 1; для листов и метров можно задать иное.
3. **ПОДТВЕРДИТЬ у владельца:** повторное добавление той же позиции в то же изделие **увеличивает количество существующей строки** (рекомендация), либо создаёт отдельную строку. Для особых случаев (отход, комментарий) остаётся полная форма по тапу «⋯» на строке.
4. Поиск получает автофокус при открытии окна; выбранная категория и поисковая строка сохраняются между добавлениями. Кнопка «Готово» закрывает окно и показывает, сколько позиций добавлено.
5. Блок «Недавние» вверху списка: 8 позиций, которые владелец добавлял чаще и последними (считается из его `order_lines`, новая таблица не нужна).
6. Запросы: оптимистичное обновление интерфейса, запись в базу с задержкой около 400 мс после последнего нажатия на степпер (один запрос на позицию, а не по запросу на каждый тап). При ошибке — откат и сообщение в строке.
7. Строки заказа получают те же степперы количества в списке «Позиции и затраты», без открытия формы.

**Тесты (Vitest, чистая логика):** слияние количества при повторном добавлении; пересчёт после изменения степпером; округление количества до 3 знаков; откат при ошибке записи; список «Недавние».

**Приёмка.** M1 достигнута; для дополнительной позиции нужно не более 2 действий (найти, нажать «+»); окно не закрывается само.

### U2. Шаблоны изделий

**Проблема.** Типовые наборы (например, кухня стандарт) каждый раз собираются вручную. Таблицы `product_templates` и `product_template_lines` в БД уже есть, в интерфейсе их нет.

**Решение.**
1. Действие «Сохранить как шаблон» в заказе: вводится название; позиции заказа группируются по `price_item_id`, количества суммируются; ручные позиции (без `price_item_id`) не входят и перечисляются в подтверждении.
2. Действие «Добавить из шаблона» в `ItemsSection` и в `PricePicker`: показывает список шаблонов; выбор добавляет все позиции с количествами из шаблона **по текущим ценам справочника** (снимок цены фиксируется триггером на вставке, как для обычных позиций).
3. Шаблон правится и удаляется на отдельном экране «Шаблоны» (в меню шапки).
4. **ПОДТВЕРДИТЬ у владельца:** масштабируются ли количества шаблона по погонным метрам изделия (например, шаблон «на 3 п.м.», изделие 4,5 п.м. → ×1,5). Рекомендация для первой версии: **нет**, количества фиксированные, владелец правит степперами. Если «да», нужно решение, какие позиции масштабируются (листы, кромка), а какие нет (петли на шкаф, подключение мойки).
5. Позиции шаблона, которых нет в активном справочнике, пропускаются с понятным сообщением.

**Тесты:** группировка при сохранении; применение с пропуском неактивных позиций; добавление в уже существующий заказ не дублирует строки (по правилу из U1).

### U3. Панель итогов и раскладка на ПК

**Проблема.** Нижняя панель на телефоне перегружена (цена, себестоимость, маржа, три кнопки, подписи 10 px); при этом она, возможно, закрывает нижнюю навигацию (**проверить**: обе элементы закреплены к низу, у панели итогов приоритет выше). На ПК интерфейс одноколоночный, шириной 896 px.

**Решение (телефон, до 1023 px).**
1. Свёрнутая панель, высота не более 64 px: **«Цена» и «Маржа %»** крупно (не меньше 18 px для цены), справа основная кнопка «Зафиксировать версию» (U4) и «▲» для раскрытия.
2. Раскрытие по тапу в нижнюю шторку на 70% высоты: затраты по категориям, сборка, технолог, резерв, себестоимость, минимальная цена при целевой марже, предупреждения. Существующий переключатель `showBreakdown` превращается в эту шторку.
3. Предупреждения расчёта (`warnings`) и ошибки показываются **цветной полосой над панелью** независимо от того, раскрыта шторка или нет.
4. Нижнюю навигацию на экране заказа скрыть; в шапке показать «← Заказы». Остальные разделы доступны из списка заказов.
5. Цвет маржи: зелёный при марже не ниже целевой, жёлтый ниже цели, красный отрицательная.

**Решение (ПК, от 1024 px).**
1. Двухколоночный вид: слева содержимое заказа (изделия, позиции), справа закреплённая карточка итогов (`sticky top-20`, ширина около 380 px) с полной детализацией, без шторки.
2. Фиксированная нижняя панель на ПК не показывается.
3. Максимальная ширина контента растёт до `max-w-6xl`.
4. Горячие клавиши: `/` ставит фокус в поиск справочника, `Enter` подтверждает форму, `Esc` закрывает окно.

**Тесты:** логика выбора цвета маржи; компонентные проверки вручную по чек-листу раздела 5.

### U4. Понятное сохранение: «Зафиксировать версию»

**Проблема.** Позиции записываются в базу сразу, а кнопка «💾 Сохранить» создаёт неизменяемую версию. Кнопок три (панель итогов, шапка вкладки «История», пустое состояние). Владелец думает, что сохраняет заказ.

**Решение.**
1. Одна основная кнопка **«Зафиксировать версию»** (в панели итогов и на ПК в карточке итогов). Дубли в «Истории» и пустом состоянии убрать, оставить там только ссылку «Зафиксировать».
2. После каждого изменения короткая подпись «Изменения сохранены» (в шапке заказа, исчезает через 2 секунды). Постоянная индикация состояния рядом с кнопкой:
   - «Совпадает с версией 3» (нейтральный);
   - «Есть изменения после версии 3» (жёлтый);
   - «Версий пока нет» (нейтральный).
3. Определение «есть изменения»: функция `isDirtySince(version, currentInput)` в `lib/`, сравнивающая нормализованные входные данные (позиции, изделия, корректировки, параметры, режим, цена договора) с `input_snapshot` последней версии, без учёта порядка записей. Использует только данные из версий (после шага A7 без подстановок).
4. Действие 🔒 «Новая версия» переименовать в «Открыть для правок» и вести через понятное окно: «Заказ утверждён. Открыть для правок? Текущий расчёт будет зафиксирован как версия N, статус изменится на “…”» (текст статуса из текущих подписей). Атомарность операций (расчёт + статус) — через RPC из шага, согласованного с агентом при реализации (**ПОДТВЕРДИТЬ** объём).

**Тесты:** `isDirtySince`: идентично → нет изменений; другое количество, цена, добавленная или удалённая позиция, другой режим, другая цена договора → есть изменения; порядок позиций не влияет.

### U5. Этапы вместо пронумерованных вкладок

**Проблема.** Экран заказа: шапка + три вкладки «1. Расчёт», «2. История версий», «3. Факт» + изделия + индивидуальные параметры + позиции + переключатель режима + детализация. Режим «Проверить договор» выглядит как настройка, хотя это следующий этап работы.

**Решение.**
1. Вместо вкладок: этапы **«Смета» → «Договор» → «Факт»** (степпер в шапке; на телефоне горизонтальные чипы).
2. **Смета** (режим `quote`): изделия, позиции, сводка. Индивидуальные параметры заказа убрать в сворачиваемый блок «Дополнительно» с пометкой «используются общие параметры» либо «изменены: маржа 20%».
3. **Договор** (режим `check_contract`): поле цены договора, карточка вывода: «Договор 850 000 ₸. Маржа 17,2% — ниже цели 18%. Минимальная цена 862 000 ₸». Кнопки «Зафиксировать версию» и «Сделать договорной» (вызывает `set_contract_baseline`).
4. **Факт** — без изменений по структуре (исправления в `FIX_SPEC_2.md`, A6).
5. **История версий** — в меню шапки «🕘 Версии (3)», открывается отдельным экраном/шторкой; из версии доступны «Сделать договорной» и просмотр состава.
6. **ПОДТВЕРДИТЬ у владельца:** должна ли кнопка «Сделать договорной» одновременно переводить заказ в статус `approved` (и блокировать правки). Рекомендация: да, с явным текстом в подтверждении.
7. **ПОДТВЕРДИТЬ у владельца:** русские подписи статусов заказа (текущие значения: draft, quoted, approved, in_production, done, cancelled) и порядок их показа в списке.

### U6. Язык и читаемость

**Глоссарий замен** (подписи в интерфейсе, коды в БД не меняются):

| Сейчас | Станет |
|--------|--------|
| режим «Рассчитать цену» / `quote` | «Смета» (этап) |
| режим «Проверить договор» / `check_contract` | «Договор» (этап) |
| «Мин. цена для маржи» | «Минимальная цена при марже 18%» (процент из параметров) |
| «Сохранить», «💾 Сохранить текущий расчёт» | «Зафиксировать версию» |
| «🔒 Новая версия» | «Открыть для правок» |
| «История расчётов», «неизменяемые версии и снимки» | «Версии расчёта» |
| «Ошибка расчёта: Необходимо указать цену по договору» (для любой ошибки) | отдельный текст на каждый код ошибки (см. A3) |

**Типографика.** Основное содержимое и числа не меньше 14 px; подписи не меньше 12 px; размеров 10–11 px не оставлять совсем. Заголовки, цены и маржа крупнее и жирнее остального.

**Зоны нажатия.** Все кнопки и иконки не меньше 44 × 44 px (через `min-h-11 min-w-11` или внутренний `padding`). Иконки ✎ и 🗑 заменить на встроенные SVG-иконки (без новых библиотек), единый набор: правка, удаление, дублирование, добавление, закрыть, меню.

### U7. Мелкие улучшения (делать вместе с другими шагами)

- **Отмена удаления:** после удаления позиции или изделия показывать «Удалено · Отменить» на 6 секунд; фактическое удаление в базе после истечения времени (вместо диалога подтверждения). Для удаления заказа и платежей подтверждающий диалог остаётся.
- **Дублирование:** «Дублировать» для позиции и для изделия (копирует позиции).
- **Ошибки:** вместо `alert`-диалогов (`DialogProvider`) для некритичных ошибок показывать сообщение в строке или короткий тост; диалог только для действий с необратимыми последствиями.
- **Ввод чисел:** при вводе суммы показывать разряды пробелом («850 000») без потери курсора; `enterKeyHint="done"` в числовых полях; запятая и точка допустимы везде, где вводится дробное число (проверить все поля, в том числе параметры и прайс).
- **Автофокус** на первое поле в каждой форме (название, количество, сумма).
- **Список заказов:** цветной чип маржи у каждого заказа (правила цвета из U3); поиск по названию, клиенту и статусу; запоминание выбранного фильтра между открытиями.
- **Порядок позиций:** внутри категории позиции сортируются по порядку добавления, возможность переупорядочивания не нужна.
- **Подтверждение крупных сумм:** при вводе цены договора, отличающейся от последнего расчёта более чем в 3 раза, показать мягкое предупреждение («Проверьте количество нулей»).

### U8. Скорость и обновления

1. **Разделение кода:** страницы подгружаются через `React.lazy` и `Suspense` (заказы, заказ, прайс, параметры); цель M5 — начальный JS не более 350 КБ.
2. **Обновление приложения:** когда service worker находит новую версию, показать «Доступно обновление · Обновить» (вместо тихой подмены при следующем открытии). Не прерывать ввод данных.
3. **Состояния загрузки:** скелетоны вместо одного общего «Загрузка…» на странице заказа; список позиций показывается, как только загружен, остальные блоки догружаются.

## 4. Что не меняется

Пакет `@kuhni/calc`, структура БД, RLS, неизменяемость версий, формат денег (целые KZT с пробелами), палитра и общий стиль (зелёный акцент, тёплый фон).

## 5. Чек-лист проверки каждого шага (владелец)

Телефон (375 px) и ПК (1280 px):
1. Создать заказ, добавить изделие, добавить 10 позиций из справочника.
2. Изменить количество степпером и вводом с запятой («3,5»).
3. Раскрыть итоги, убедиться, что цена, себестоимость и маржа читаются без увеличения.
