# ТЗ: интерфейс калькулятора (UI v1)

Документ для AI-агента-разработчика. Продолжение `backend_spec.md`: бэкенд (шаги 0-6) готов, теперь нужен интерфейс, в котором владелец вводит заказы, видит расчёт и вносит факт. Владелец код не пишет, он проверяет результат на телефоне и ПК и принимает решения по логике.

## 0. Правила работы агента

1. Работать маленькими шагами по разделу 8. После каждого шага: что сделано, как проверить, ждать подтверждения. Коммит после каждого рабочего шага.
2. **Расчёт не переписывать.** Интерфейс вызывает готовый `packages/calc`. Никаких копий формул в компонентах.
3. Не придумывать бизнес-логику. Всё неясное спросить у владельца.
4. Секреты не в Git. В браузерном коде используется только публичный (anon) ключ Supabase, `service_role` в интерфейсе недопустим.
5. **Без Docker и локального Supabase**: рабочая машина слабая (8 ГБ ОЗУ). Разработка идёт против облачного проекта Supabase, лёгкий dev-сервер Vite.
6. Деньги в тенге (KZT), целые числа, с разделителем тысяч (`886 000`). Количества с точностью до 3 знаков.

## 1. Цель и границы v1

**Цель:** владелец может за несколько минут собрать расчёт заказа с телефона, увидеть цену и маржу, сохранить версию расчёта, а после выполнения внести фактические расходы и увидеть план против факта.

**Входит в v1:** вход, справочник цен, параметры, заказы, редактор заказа с живым расчётом, сохранение версий расчёта, факт и поступления, план/факт, установка как приложения (PWA).

**Не входит в v1** (отдельные ТЗ): чек-листы, роль `staff`, доступ агентов (Edge Function), шаблоны изделий в интерфейсе, аналитика по многим заказам, фото и файлы, исторический импорт, резервные копии.

## 2. Стек и развёртывание

- React + TypeScript + Vite, Tailwind CSS (без тяжёлых UI-библиотек). Если агент предложит другое, обосновать.
- Supabase JS client, вход через Supabase Auth (email и пароль).
- PWA: манифест, иконка, установка на экран телефона. Офлайн-режим в v1 не нужен, но оболочка приложения должна открываться без ошибок при слабой сети.
- Хостинг: Cloudflare Pages, Vercel или GitHub Pages (бесплатно). Автодеплой из Git.
- Тесты: Vitest для логики вокруг `packages/calc`, один сквозной тест главного сценария (раздел 7).

## 3. Дизайн-принципы

1. **Mobile-first**, проверять на ширине 375 px, затем масштабировать на ПК (на ПК двухколоночный вид там, где есть смысл).
2. Основные действия достижимы за ≤3 тапа: «новый заказ», «добавить позицию», «сохранить расчёт», «внести расход».
3. Поля ввода чисел открывают цифровую клавиатуру (`inputmode="decimal"`), крупные кнопки, не меньше 44 px по высоте.
4. Итог расчёта (цена, себестоимость, маржа %) всегда виден, на телефоне закреплён внизу экрана.
5. Предупреждения расчёта (`warnings`) показываются заметно, но не блокируют работу.
6. Все тексты на русском. Подписи категорий: Материалы, Цех, Фурнитура, Транспорт, Работа, Остальное.

## 4. Экраны

### 4.1 Вход
Email, пароль. Регистрация в интерфейсе отсутствует. После входа переход к списку заказов.

### 4.2 Список заказов
- Карточки: название, статус, цена по договору, цена и маржа % последнего расчёта, дата.
- Поиск по названию, фильтр по статусу, сортировка по дате.
- Кнопка «Новый заказ».

### 4.3 Карточка заказа (главный экран)
Вкладки или секции:

1. **Расчёт.** Изделия внутри заказа (кухня, шкаф, другое), у каждого позиции. Внизу сводка: затраты по категориям, процентные статьи (сборка, технолог, резерв), себестоимость, цена, маржа, `min_price_for_target_margin`, предупреждения.
   - Переключатель режима: «Рассчитать цену» (`quote`) и «Проверить договор» (`check_contract`, использует цену по договору).
   - Редактируемые поля заказа: название, клиент (метка, без контактов), статус, цена по договору, переопределение параметров для этого заказа (`orders.settings`: режимы и проценты сборки/технолога, маржа, отходы).
   - Корректировки: «скидка», «срочность», «риск» и т.п. (`adjustments`) с комментарием.
   - Кнопка «Сохранить расчёт» создаёт новую версию в `calculations`.
2. **История расчётов.** Список версий (номер, дата, режим, цена, маржа). Просмотр версии с параметрами, использованными тогда. Сравнение двух версий не обязательно в v1.
3. **Факт.** Расходы по заказу (форма и список), поступления от клиента, сводка план/факт.

### 4.4 Редактор позиции
- Выбор позиции из справочника с поиском по названию и фильтром по категории (на телефоне полноэкранный список).
- Поля: количество, единица (из справочника, не редактируется), отход (по умолчанию из параметров, можно переопределить), комментарий.
- Ручная позиция: категория, название, единица, количество, цена за единицу, помечается как ручная. Нужна для транспорта, столешницы, мелочей фурнитуры.
- Цена за единицу копируется из справочника в `order_lines.unit_price` в момент добавления позиции (снимок).

### 4.5 Справочник цен
- Список по категориям с поиском, цена редактируется прямо в списке.
- Карточка позиции: название, единица, цена, поставщик, отход (`waste_applicable`, `waste_kind`), `counts_for_technolog`, примечание, активна/архив.
- «История цены» (из `price_history`): дата, старая, новая.
- Добавление новой позиции. Удаление запрещено, только архивирование (чтобы не ломать старые заказы).

### 4.6 Параметры
Список параметров с описанием, значением и единицей, редактирование с сохранением. Для процентов вводить человеческий формат (14,5%), хранить долей (0,145). Предупреждать, если значения дают знаменатель формулы ≤ 0,05.

### 4.7 Факт и поступления
- Расход: дата, категория, название, сумма, переключатель «переделка» (при включении обязательное поле «причина»), примечание.
- Поступление: дата, сумма, примечание.
- Сводка: по каждой категории план (последняя сохранённая версия расчёта) против факта, отдельной строкой сумма переделок, остаток по оплате (договор минус поступления), фактическая маржа.
- Личные траты вносить нельзя. В форме показать короткую подсказку, что сюда вносятся только расходы по этому заказу.

## 5. Правила и логика

1. **Снимок цен.** Цена позиции фиксируется при добавлении. Если цена в справочнике потом изменилась, в редакторе показывается пометка «цена в справочнике изменилась» и кнопка «Обновить цены» (только для заказов в статусе `draft` и `quoted`, с подтверждением и показом разницы итога).
2. **Расчёт в реальном времени.** Любая правка позиции, параметров или корректировки сразу пересчитывает сводку через `packages/calc`, без записи в базу. Версия в `calculations` создаётся только кнопкой «Сохранить расчёт».
3. **Статусы.** `draft`, `quoted`, `approved`, `in_production`, `done`, `cancelled`. После `approved` позиции и параметры блокируются от случайной правки: изменение возможно только через явное «Создать новую версию расчёта».
4. **Ошибки расчёта** (например, знаменатель ≤ 0,05) показываются понятным текстом, а не падением экрана.
5. **Потери и переделки** не входят в расчёт цены и отображаются только на вкладке «Факт».
6. **Доступ.** Все запросы идут под пользователем (RLS). Если запрос отклонён из-за прав, показать понятное сообщение.
7. **Удаление заказа** только через архив/отмену статусом `cancelled`, физически не удалять.

## 6. Не делаем в v1

Чек-листы, шаблоны изделий в интерфейсе, роль `staff`, API для агентов, фото и файлы, графики аналитики по всем заказам, экспорт в Excel/PDF (допускается простая кнопка «Копировать итог текстом» для отправки клиенту, если останется время).

## 7. Тесты и приёмка

Главный сквозной сценарий (автотест и ручная проверка на телефоне):

1. Вход.
2. Создать заказ, добавить кухню на 3 погонных метра.
3. Добавить позиции эталонного примера из `backend_spec.md` (раздел 7).
4. Режим «Рассчитать цену»: цена **886 000**, себестоимость **726 250**, маржа ≈ **18,03%**.
5. Сохранить расчёт, версия 1 появилась в истории.
6. Изменить цену ЛДСП в справочнике: сохранённая версия 1 и позиции заказа не изменились, в заказе появилась пометка об изменении цены.
7. Режим «Проверить договор» с договором 850 000: маржа ≈ **15,34%**, предупреждение, что договор ниже минимальной цены 886 000.
8. Внести расход с флагом «переделка» и причиной, поступление: сводка план/факт обновилась, переделка показана отдельно.

Дополнительно: интерфейс не ломается на ширине 375 px; ни один экран не доступен без входа; в браузерном коде нет `service_role`; установка на экран телефона работает.

## 8. Шаги и критерии готовности

| № | Шаг | Готово, когда |
|---|---|---|
| U0 | Каркас: Vite, Tailwind, Supabase client, вход, деплой на бесплатный хостинг, PWA-оболочка | приложение по ссылке открывается и на телефоне, и на ПК, вход работает, установка на экран телефона работает. Шаг U0 должен включать подключение packages/calc к приложению (workspace в репозитории). |
| U1 | Справочник цен: список, поиск, правка цены, история, добавление и архив | цена меняется в интерфейсе и видна в базе, в истории появляется запись |
| U2 | Параметры: список и редактирование | значения сохраняются, некорректные значения подсвечиваются |
| U3 | Список заказов и создание заказа | заказ создаётся и открывается с телефона |
| U4 | Карточка заказа: изделия, позиции, ручные позиции, корректировки, живой расчёт | эталонный пример даёт цену 886 000 и маржу ≈ 18,03% |
| U5 | Сохранение версий расчёта и история, пометка об изменении цен, блокировка после `approved` | шаги 5-7 сквозного сценария проходят |
| U6 | Факт и поступления, сводка план/факт | шаг 8 сквозного сценария проходит |
| U7 | Полировка для телефона, сообщения об ошибках, пустые состояния, быстрые действия | чек-лист раздела 3 выполнен на реальном телефоне |

После U7: резервные копии (шаг 8 бэкенд-ТЗ) **до ввода первых реальных заказов**, затем исторический импорт, затем доступ для агентов и чек-листы.
